## Розглянуті аргументи

| Роль | Позиція | Аргумент |
|---|---|---|
| Архітектор | **за**, з умовою | Автоматичний контроль CBO/DIT — єдиний спосіб утримати межі ADR-0001 у довгій перспективі. Зауваження: вибір `javalang` як парсера ніде не зафіксований (ADR немає), а R1 пом'якшено лише текстом у coding-standards — це ризик, який варто закрити окремо |
| Лідер QA | **за** | Негативний тест показав, що гейт справді блокує порушення (CBO 8 > 7 → FAIL). Регресійний ризик для коду нульовий: `src/` не змінюється. Вимога — перевірити повний run конвеєра після злиття |
| SRE | **за**, з умовою | Runtime-вплив відсутній (API, RB-001, алерти A-01…A-03 не зачіпаються). Але `deploy` почне залежати від ще одного інструмента: якщо гейт впаде через збій самого інструмента, публікація сайту зупиниться → потрібен перевірений план відкату (RFC §4) |
| Product Owner | **за** | Цінність: менше ручної праці супроводжувача, захист якості для майбутніх контриб'юторів. Термін — у межах ЛР12, без впливу на API-клієнтів |

## Рішення

**ПОГОДЖЕНО З УМОВАМИ** (4 голоси «за» з 4).

| # | Умова виконання | Перевірка |
|---|---|---|
| У1 | Обидва гейти локально на `main` дають PASS, негативний тест — FAIL | лог `rfc001-gate-verification.log` — **виконано до засідання** |
| У2 | План відкату (RFC §4) — у заявці до злиття | RFC-001 §4 |
| У3 | ISD D3, README (DoD), CONTRIBUTING, CHANGELOG оновлено **в тому самому коміті** (DoD ЛР11) | рев'ю коміту реалізації |
| У4 | Після злиття — повний зелений run `docs.yml` (build, api-contract, oo-gates, deploy) | GitHub Actions |
| У5 | Ризик R1 приймається як **залишковий**; питання ADR для інструментів аудиту вноситься в беклог супроводу | беклог [плану супроводу](../maintenance-plan.md) |

**Термін виконання:** до 2026-11-23 23:59 UTC. **Відповідальний:** Yehor Ishchuk.

## Регламент CCB

| Пункт | Правило |
|---|---|
| Періодичність | щотижня, понеділок 10:00 (Київ); **позачергово** — для термінових змін (протягом 2 год після інциденту SEV-1/SEV-2) |
| Подання RFC | повна форма (§1 RFC-001 як зразок), Impact Analysis на 7 рівнів, Risk Exposure, план відкату; нормальна зміна — щонайменше за 24 год до засідання |
| Стандартні (попередньо погоджені) зміни | лише документація без зміни поведінки при зеленому конвеєрі `docs.yml` — без CCB, за DoD ЛР11 |
| Кворум | усі чотири ролі (архітектор, QA, SRE, Product Owner); рішення — більшістю з обов'язковим мотивуванням кожної ролі |
| Варіанти рішень | погоджено · погоджено з умовами · відхилено · відкладено (з датою повторного розгляду) |
| **Change freeze** | якщо бюджет будь-якого SLO витрачено на 100 % (`error_budget_policy` у slo.yaml) — CCB погоджує лише «термінові» зміни, що підвищують стабільність; на 50–100 % — нормальні зміни тільки з перевіреним планом відкату і голосом SRE |
| Звітність | на кожному засіданні — витрата бюджетів помилок (`tools/slo_budget.py --consumed …`) і статус відкритих CAPA |
