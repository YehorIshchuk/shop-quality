## 2. Impact Analysis — сім рівнів впливу

| Рівень | Вплив | Конкретні артефакти |
|---|---|---|
| **1. Вимоги** | Поведінка системи для користувача API **не змінюється**. Змінюється сценарій контриб'ютора: PR, що порушує пороги ЛР8, отримує червоний статус і не потрапляє на сайт | README → таблиця Definition of Done (новий рядок «OO-архітектура»); сценарій «відкрити PR» у [[CONTRIBUTING]] |
| **2. Архітектура** | Компоненти й зв'язки SDD не змінюються. Змінюється вузол **D3 конвеєр** в ISD: OO-гейти переходять з локальних скриптів у хмарний CI. **Новий ADR не потрібен** — це реалізація контролю, вже передбаченого ADR-0001 («межі контролюються гейтом») | [[isd]] D3 (таблиця стадій і схема), [ADR-0001](../architecture/adr/0001-hexagonal-ports-and-adapters.md) без змін |
| **3. Код** | Радіус ураження — **лише конфігурація конвеєра**; `src/main` і `src/test` не змінюються | `.github/workflows/docs.yml` (job `oo-gates`, `deploy.needs`), `.gitignore` (`reports/oo/ci/`); `scripts/oo-gate-*.sh`, `tools/oo_metrics.py`, `tools/requirements.txt` — використовуються без змін |
| **4. API** | `docs/api/openapi.yaml` **не змінюється** — ні additive, ні breaking; міграційний гайд не потрібен | контракт 1.0.0 |
| **5. Дані** | Міграцій схеми немає (in-memory, ADR-0002). Нові дані — лише артефакт збірки `oo-report` (JSON/MD/HTML, retention 14 днів), у репозиторій не комітиться | `reports/oo/ci/` у `.gitignore` |
| **6. Тести** | Мінімальний регресійний набір: (а) обидва гейти локально на `main` → PASS; (б) **негативний тест** — поріг CBO 7 при фактичному 8 → FAIL, exit 1; (в) повний run `docs.yml` на GitHub: build, api-contract, **oo-gates**, deploy — зелені; JUnit не перезапускається (код не змінюється) | [лог перевірки](https://github.com/YehorIshchuk/shop-quality/blob/main/docs/reports/lab12/rfc001-gate-verification.log): 11/11 + 3/3 PASS, негативний — FAIL |
| **7. Документація та експлуатація** | Оновити ISD D3, README (DoD), CONTRIBUTING (чек-лист), CHANGELOG; runbook-ів і алертів API зміна не зачіпає; час конвеєра +≈ 30 с | DoD ЛР11: усі документи — у тому самому коміті реалізації |

## 3. Оцінка ризику (Risk Exposure = ймовірність × наслідки)

Шкала: ймовірність 1 (рідко) … 5 (майже напевно); наслідки 1 (непомітно) … 5 (простій сервісу / втрата даних).
RE 1–5 — низький, 6–12 — середній, 15–25 — високий.

| # | Ризик | Ймовірність | Наслідки | RE | Пом'якшення |
|---|---|---|---|---|---|
| R1 | `javalang 0.13.0` розбирає синтаксис лише до Java 8: новий код із `record` / switch-виразами / text blocks зробить гейт **червоним без реального порушення** і заблокує публікацію сайту | 2 | 3 | **6** | заборона в [[coding-standards]] §4 (лише текст — автоматичного контролю немає) |
| R2 | Конвеєр подовжиться (+ встановлення javalang і два прогони аналізу) | 5 | 1 | 5 | паралельний job, кеш pip |
| R3 | Встановлення `javalang` на раннері не вдасться (PyPI недоступний) | 1 | 3 | 3 | версія зафіксована в `tools/requirements.txt`; повторний запуск job |

**Підсумковий клас ризику — середній (max RE = 6)** → нормальна зміна, обов'язковий розгляд CCB.

## 4. План відкату

1. `git revert <коміт реалізації>` → `git push` (≈ 2 хв): job `oo-gates` зникає, `deploy` знову залежить лише від `build` і `api-contract`.
2. Альтернатива без revert (термінова): у `docs.yml` для job `oo-gates` поставити `if: false` окремим комітом.
3. Перевірка відкату: наступний run `docs.yml` зелений, сайт опубліковано.

Час відкату ≤ 5 хв; даних, які треба повертати, немає.
