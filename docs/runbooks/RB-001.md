# RB-001 · Розгортання версії Shop Core API з health-перевіркою і відкатом

> Черговий о третій ночі не читає код — він виконує цей документ зверху вниз.
> Команди перевірено запуском 2026-11-22 ([лог](https://github.com/YehorIshchuk/shop-quality/blob/main/docs/reports/lab12/deploy-rollback.log)).

| Поле | Значення |
|---|---|
| Ідентифікатор | RB-001 |
| Сервіс | D1 · Shop Core App + HTTP API ([[isd]] §4 D1) |

| Подія | Розділ |

Повний перелік умов спрацювання — [каталог алертів](alerts.md).

## 2. Передумови

- Права: локальний обліковий запис на станції розгортання; читання репозиторію (`git fetch --tags`).
- Інструменти: JDK 17+, Maven 3.9+, Git, `curl` (перевірка: `java -version && mvn -v && git --version`).
- Порт `8080` (`SHOP_HTTP_PORT`) вільний або зайнятий попередньою версією, якою керує скрипт.
- Тег релізу пройшов конвеєр `docs.yml` (зелений run на GitHub Actions).

## 3. Рівень автоматизації і чому саме 1

| Рівень | Що означало б для D1 | Рішення |
|---|---|---|
| 0 — ручний | 6 команд вручну: archive, build, kill, nohup, curl, запис версії | ❌ помилка в будь-якому кроці = простій |
| **1 — скриптований** | `deploy-api.sh <тег>` / `rollback` / `status`: кроки детерміновані, health-перевірка вбудована | ✅ **обрано** |
| 2 — «одна кнопка» | workflow_dispatch у GitHub Actions з деплоєм на сервер | ❌ немає сервера: D1 працює на станції розробника (ISD §1) |
| 3 — self-healing | супервізор (launchd/systemd) перезапускає і відкочує сам | ❌ для одного екземпляра на ноутбуці — надмірно; кандидат при переході на сервер |

Рівень 1 знімає ризик пропуску кроку, а людина лишається там, де потрібне рішення — чи відкочувати.

## 4. Покрокові дії

### 4.1 Підготовка

```bash
cd ~/Desktop/shop-quality
git fetch origin --tags
git tag --list 'v*' --sort=-creatordate | head -3      # який тег розгортаємо
./scripts/deploy-api.sh status                         # що працює зараз (current / previous / health)
```

### 4.2 Розгортання

```bash
./scripts/deploy-api.sh v1.1.0
# 2026-11-22T18:49:42Z  збираю v1.1.0 …  запускаю v1.1.0 на :8080
# 2026-11-22T18:49:45Z  HEALTH OK за 1 с — розгорнуто v1.1.0 (попередня: v1.0.0)
```

Скрипт: `git archive <тег>` у `~/shop-deploy/releases/<тег>` → збірка (`mvn -B -q -DskipTests package`, тести вже
пройдені в CI) → зупинка поточного PID → запуск нового → до 30 с очікування `GET /api/health = UP`.
Код виходу `2` = health не піднявся → **одразу §7**.

### 4.3 Перезапуск поточної версії (A-01)

```bash
./scripts/deploy-api.sh "$(cat ~/shop-deploy/current)"
```

## 5. Верифікація — як переконатися, що ціль досягнута

```bash
./scripts/deploy-api.sh status                                         # health: UP, current: v1.1.0
curl -s localhost:8080/api/orders/ORD-1                               # 200 + JSON замовлення
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE localhost:8080/api/health   # 405 (контракт ЛР11)
python3 tools/sli_probe.py --url http://localhost:8080 --requests 500 --check  # ALERT CONDITIONS: OK
```

Критерій успіху: усі чотири команди дають очікуваний результат, `ALERT CONDITIONS: OK` (5xx ≤ 1 %, p95 < 300 мс).

## 6. Діагностика (A-03 і невдала верифікація)

```bash
tail -50 ~/shop-deploy/logs/api-$(cat ~/shop-deploy/current).log   # SEVERE / стек-трейси
lsof -iTCP:8080 -sTCP:LISTEN                                          # хто тримає порт
python3 tools/sli_probe.py --url http://localhost:8080 --requests 2000 # p95/p99, коди відповідей
```

## 7. Відкат

```bash
./scripts/deploy-api.sh rollback
# ВІДКАТ на v1.0.0 …  HEALTH OK за 1 с — розгорнуто v1.0.0 (попередня: v1.1.0)
./scripts/deploy-api.sh status
```

Потім повторити §5. Відкат не потребує збірки (реліз попередньої версії вже лежить у `releases/`) — ≈ 10 с.
Дані замовлень після перезапуску засіваються заново (in-memory, [[0002-in-memory-storage-with-csv-export|ADR-0002]]).
