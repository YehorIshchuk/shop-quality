# План супроводу Shop Quality (SWEBOK Software Maintenance)

Документ задає, **хто, як швидко і за якими правилами** підтримує систему після релізу v1.1.0: лінії підтримки,
ескалацію, відомі проблеми та пріоритети вдосконалення legacy-коду. Терміни реакції узгоджені з
[slo.yaml](slo.yaml) і [каталогом алертів](runbooks/alerts.md).

## 1. Об'єкт і типи супроводу

| Об'єкт | Компонент ISD | Цільовий рівень |
|---|---|---|
| HTTP API замовлень | [D1](architecture/isd.md#d1) | SLO `api-availability` 99.5 %, `api-latency` 99.0 % |
| Конвеєр якості і сайт документації | D3, D5, GitHub Actions/Pages | SLO `pipeline-verdict` 95 % |
| Legacy `tools/oo_metrics.py` | D5 | [документація і борг](legacy/oo-metrics.md), [ADR-0004](architecture/adr/0004-javalang-java8-syntax-limit.md) |

Типи супроводу за SWEBOK (ISO/IEC 14764): **коригувальний** (дефекти, інциденти → INC/PM/CAPA), **адаптивний**
(нові JDK, оновлення дій GitHub і залежностей — через RFC), **удосконалювальний** (пріоритети §6), **превентивний**
(щотижневий плановий запуск конвеєра, restore drill, перегляд Known Issues).

## 2. Лінії підтримки

| Лінія | Хто (роль) | Що робить | Інструменти | Межа повноважень |
|---|---|---|---|---|
| **L1** | черговий (будь-який учасник за графіком) | приймає алерт або звернення, перевіряє health і статус конвеєра, виконує дії з runbook до рівня «перезапуск / повтор job», фіксує інцидент | `curl /api/health`, `sli_probe --check`, вкладка Actions, [RB-001 §4.3](runbooks/RB-001.md#43-перезапуск-поточної-версії-a-01) | не змінює код і конфігурацію |
| **L2** | SRE / DevOps | діагностика за runbook, відкат релізу, обхідні рішення, присвоєння SEV, керування інцидентом, restore з резервної копії | [RB-001](runbooks/RB-001.md), [RB-002](runbooks/RB-002.md), `deploy-api.sh rollback`, `restore-drill.sh` | відкат і обхід — так; зміна коду — лише revert |
| **L3** | розробник-власник компонента / архітектор | виправлення коду, першопричина (5 Whys), CAPA, зміни інструментів і ADR | IDE, тести, `tools/tests`, RFC/CCB | будь-яка зміна — через PR і (для нормальних змін) CCB |

**Критерії передачі між лініями:**

| Перехід | Коли передавати |
|---|---|
| L1 → L2 | runbook не відновив сервіс за **15 хв** (SEV-1) / **30 хв** (SEV-2); або причина поза кроками runbook; або потрібен відкат; або інцидент SEV-1 — одразу з паралельним повідомленням |
| L2 → L3 | потрібна зміна коду, не revert; або відкат неможливий / не допоміг; або повторення того самого алерту ≥ 2 рази за 7 днів; або збій інструмента без відомого обходу (A-05, гілка «guard чистий, а код 3») |
| L3 → CCB | виправлення — нормальна зміна (не термінова); або потрібно прийняти залишковий ризик (лише з власником і терміном); або витрачено ≥ 50 % бюджету помилок |
| Повернення L3 → L1 | виправлення задеплоєно, верифікація runbook пройдена, інцидент закрито; L1 спостерігає 24 год |

## 3. Матриця ескалації

| SEV | Приклад | Час реакції (підтвердження) | Ціль відновлення / обходу | Кому | Канал |
|---|---|---|---|---|---|
| **SEV-1** | A-01 API недоступний; втрата даних; порушення SLA `api-*` | **15 хв**, 24/7 | обхід ≤ 1 год (RTO D1 ≤ 5 хв — [ISD §6.1](architecture/isd.md)) | L1 → **одразу** L2 і L3; Product Owner — інформування через 30 хв | телефонний дзвінок + GitHub Issue з міткою `incident:sev1`; статус кожні 30 хв |
| **SEV-2** | A-02 частка 5xx > 1 %; A-05 конвеєр без вердикту; deploy заблоковано | **1 год** у робочий час | обхід ≤ 4 год, виправлення ≤ 1 роб. день | L1 → L2; L3 — якщо за 1 год немає обходу | GitHub Issue `incident:sev2` + повідомлення в чат команди |
| **SEV-3** | A-03 латентність p95 ≥ 300 мс; A-04 витрата ≥ 50 % бюджету; некритичний інструмент | наступний робочий день | виправлення ≤ 5 роб. днів або через RFC | L2 (власник); A-04 — Change Manager → CCB | GitHub Issue `incident:sev3` |
| **SEV-4** | косметичні дефекти документації, запит на вдосконалення | у межах тижневого циклу | за пріоритетом беклогу | L3 | Issue з шаблоном / RFC |

Після інциденту **SEV-1/SEV-2** — Post-Mortem протягом 2 робочих днів і позачергове засідання CCB протягом 2 год
([регламент](changes/CCB-001.md#регламент-ccb)); зразок — [INC-001](incidents/INC-001.md) → [PM-001](incidents/PM-001.md).

## 7. Звітність і перегляд плану

- Щотижня (CCB, понеділок): витрата бюджетів помилок (`tools/slo_budget.py --consumed …`), статус CAPA, нові Known Issues.
- Щомісяця: restore drill (`scripts/restore-drill.sh`), перевірка RTO ≤ 15 хв.
- План переглядається щокварталу або після кожного інциденту SEV-1/SEV-2.
