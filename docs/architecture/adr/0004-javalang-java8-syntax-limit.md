# ADR-0004: OO-гейти на javalang 0.13.0 і обмеження синтаксису коду до Java 8

- **Номер:** 0004
- **Статус:** Accepted
- **Дата рішення:** 2026-11-22 (CAPA-3 з [PM-001](../../incidents/PM-001.md); фіксує рішення, яке з ЛР8 існувало лише як
  речення в [coding-standards §4](../../developer/coding-standards.md#4-конвенції-java))
- **Автор / власник:** Yehor Ishchuk
- **Зв'язок:** закриває борг D-1 і частково A-1 у [документації legacy-модуля](../../legacy/oo-metrics.md#4a-реєстр-технічного-боргу-і-ризиків);
  не змінює [ADR-0001](0001-hexagonal-ports-and-adapters.md)
- **Зачеплені документи:** [ISD D5](../isd.md#d5), [coding-standards §4](../../developer/coding-standards.md#4-конвенції-java),
  [план супроводу](../../maintenance-plan.md), [RB-002](../../runbooks/RB-002.md)

## Контекст

Архітектурні пороги ЛР8 (CBO ≤ 8, LCOM ≤ 0.2, DIT ≤ 1, NMO = 0) рахує `tools/oo_metrics.py` на бібліотеці
`javalang 0.13.0` (останній реліз 2020-03-28, PyPI). Вона розбирає синтаксис лише до Java 8 (+ `var`), тоді як
проєкт компілюється JDK 17. З ЛР8 обмеження трималося на пам'яті автора і одному реченні в coding-standards;
RFC-001 переніс гейти в CI і прийняв ризик R1 як залишковий без власника. 2026-11-22 коректний рефакторинг на `record`
зупинив конвеєр ([INC-001](../../incidents/INC-001.md)).

## Розглянуті альтернативи

| # | Варіант | Плюси | Мінуси |
|---|---|---|---|
| A | Дозволити Java 17, вимкнути OO-гейти до міграції | розробники вільні | архітектурний захист ЛР8 зникає на невизначений час |
| B | **Лишити javalang, обмежити синтаксис Java 8 і перевіряти це автоматично (`java_syntax_guard.py`), мігрувати парсер за планом** | гейти працюють сьогодні; порушення дає зрозумілий FAIL до запуску парсера; час на міграцію | частина можливостей Java 17 тимчасово недоступна |
| C | Негайно переписати аналізатор на `tree-sitter-java` | повна підтримка синтаксису | ~1 тиждень роботи без тестової бази для порівняння метрик; ризик тихої зміни значень CBO/LCOM |
| D | Брати метрики з SonarQube (D4) | промисловий парсер | D4 не працює в CI (≥ 23 ГБ диска, JDK 21), немає CBO/LCOM-HS у потрібному вигляді |

## Рішення

Обрано **B**:

1. Код у `src/` пишеться синтаксисом Java ≤ 8 (+ `var`). Заборонено: `record`, `switch`-правила `case ->` і `yield`,
   text blocks, `sealed`/`permits`, pattern matching `instanceof`.
2. Правило перевіряє `tools/java_syntax_guard.py` — у CI (job `oo-gates`) і в `scripts/oo-audit.*` перед `oo_metrics.py`.
3. Якщо парсер усе ж не впорався, `oo_metrics.py` повертає **код 3** (OO TOOL ERROR), а не 1 — збій інструмента
   відрізняється від вердикту, спрацьовує алерт A-05 → [RB-002](../../runbooks/RB-002.md).
4. **План міграції** (власник — Yehor Ishchuk): до **2027-01-31** — еталонні значення метрик на поточному коді
   (fixtures у `tools/tests`); до **2027-02-28** — парсер на `tree-sitter-java` з тим самим JSON-виходом і
   рівністю метрик з еталоном; після цього — новий ADR, що замінює цей (Superseded), і зняття обмеження.

## Наслідки

- (+) Конвеєр не «падає» на легітимному коді без пояснення: розробник бачить `file:line` і підказку ще до гейта.
- (+) Обмеження стало явним рішенням з власником і терміном, а не залишковим ризиком без господаря.
- (−) До міграції не можна використовувати сучасний синтаксис; кожен виняток — лише через RFC.
- (−) Регулярні вирази guard можуть мати хибні спрацювання; узгодженість guard і парсера перевіряє тест
  `test_guard_agrees_with_parser_on_fixtures`.
